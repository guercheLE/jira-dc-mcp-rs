# Documentation gaps found in this repo's history

This repo does **not** have a full PRD/architecture doc set. Its `docs/`
folder only holds three files: `SCHEMA_VERSIONS.md` (a generated table of
which Jira DC API version maps to which embedded store/schema file),
`mcp-prompts-workflow-plan.md`, and `mcp-prompts-workflow-expansion-plan.md`
(two feature-design docs for the MCP prompts capability, written after the
fact by an agent doing the corresponding implementation work). The README
covers install/usage/config/observability but was never a planning
document — it was written and repeatedly patched to describe behavior that
already existed. That narrower baseline only changes *what local doc* this
analysis compares against; it does not change how thoroughly the git
history itself was mined — the full ~102-commit, 44-release history was
walked commit by commit below.

This repo is generated by a separate tool, **mcpify** (source at
`~/Documents/GitHub/mcpify`, not modified as part of this analysis, though
its own `docs/` folder — `product-brief.md`, `prd.md`, `architecture.md`,
and the versioned `docs/vN-implementation-plan.md` files — *was* read for
every entry below tagged `(shared mcpify-template gap)`). Many `fix:`
commits below turn out to be patches for bugs that live in mcpify's shared
Rust code-generation templates — the same auth/config/logging/CI/store-
embedding scaffolding is regenerated into every mcpify-produced MCP server
(`bamboo-mcp-rs`, `bitbucket-dc-mcp-rs`, `confluence-dc-mcp-rs`,
`github-mcp-rs`, `octopus-mcp-rs`, `postgres-mcp-rs`, `spotify-mcp-rs`,
`sqlserver-mcp-rs`, `topdesk-mcp-rs`, and this repo). For every entry
tagged that way, the "Doc gap" section below now states specifically what
mcpify's own `docs/prd.md`/`docs/architecture.md` (or a `vN-
implementation-plan.md`) should have specified but didn't — that's the
actual root cause that then required a fix here (and, confirmed via
matching commits, in mcpify's own generator and usually in sibling repos
too) — rather than just noting that this repo's own three local docs don't
cover it. Entries tagged **(repo-specific)** are genuine gaps in *this*
repo's own Jira-DC-domain documentation, and were checked only against
this repo's own docs, per the original methodology.

mcpify has its own `docs/DOC-GAPS.md` and `docs/CHANGELOG.md`, written this
same session using the identical methodology, grounded in mcpify's own git
history. Every shared-tagged entry below was cross-checked against both.
Where a match exists, this file points at it directly instead of
re-deriving a differently-worded version of the same root cause. Where a
shared-tagged entry below is **not** covered there — including several
cases where the fix is confirmed present in mcpify's own `CHANGELOG.md`
but was never written up as its own `docs/DOC-GAPS.md` root-cause entry —
that's called out explicitly as a new finding, worth a fresh entry on the
generator side. One entry originally tagged shared (the v0.1.1 `.gitignore`
fix) was **downgraded to repo-specific** after this cross-check: mcpify's
own `.gitignore.tera` history shows no evidence it ever carried the bug
this repo hit, so it doesn't appear to be inherited from the generator —
see that entry for the investigation.

## Lessons for future docs

1. **Write down the runtime/transport contract before writing code, not
   after a client breaks.** The single most expensive gap in this repo's
   history (v0.2.7) was "stdout carries MCP JSON-RPC frames on stdio
   transport, so nothing else may ever write to it" — an absolute
   constraint that wasn't written anywhere until a log line broke a real
   client's connection. mcpify's own `docs/prd.md` REQ-2.3.1 ("Logging")
   specifies structured JSON logging with secret redaction but never
   connects it to REQ-1.4 ("Transport Configuration"); mcpify's own
   `docs/DOC-GAPS.md` independently arrived at the identical lesson
   (its Lessons item 1: "Specify transport/mode-aware behavior explicitly
   for anything touching shared OS resources"). Two independent gap
   analyses — this repo's and the generator's own — converging on the same
   requirement-writing pattern is a good sign of how general it is: any new
   MCP server's design doc should open with an explicit transport-contract
   section (what owns stdout, what owns stderr, what's allowed to block,
   what must be non-interactive), not leave it implicit.

2. **Give embedded/generated multi-version assets a distribution &
   lifecycle doc up front, sized against real limits.** The store-file
   saga (v0.2.1 → v0.2.2 → v0.2.3) and the crates.io package-size cliff
   (v0.2.5, two failed publish attempts before anyone checked the limit)
   both trace back to never having written down, before the first release:
   where each embedded file lives at runtime, how it's cached/invalidated,
   and what byte budget it has against every distribution channel
   (crates.io's 10MiB limit, Docker image size, binary-install size).
   mcpify's own `docs/architecture.md` §5 ("Multi-Version Spec Support")
   documents the *naming* scheme for per-version store files in detail but
   never budgets their size, and mcpify's own `docs/DOC-GAPS.md` Lessons
   items 2 and 4 independently name both halves of this same gap (CWD-
   relative paths; "self-contained" blobs with no cost budget) — but
   neither of those two lessons, nor any dated entry there, covers the
   *third* trigger of the identical crates.io-cap pattern this repo hit
   (too many embedded per-version store files, as opposed to schema `$ref`
   duplication). Write the budget table once, check every future trigger
   of it against that one table, not per-incident.

3. **A decision to hand-patch generated code is a documentation
   liability unless it's paired with an upstream plan.** Every time this
   repo hand-fixed something that also lives in mcpify's templates (logging
   target, credential normalization, mutex-poisoning recovery, the OAuth2
   fallback, Content-Length on empty bodies, CI TTY assumptions...), the fix
   risked being silently reintroduced by the next `mcpify sync` unless it
   was also pushed upstream. The v0.5.0 sync commit confirms this happened
   for real — hand-authored README sections were "silently dropped by
   sync's older thin templates" until the generator itself was fixed
   (mcpify's own v0.10.0, and the closely related v0.10.2 "preserve
   project name when re-syncing" fix two releases later, show the
   generator's own team rediscovering this exact class of regression more
   than once too). Any hand-patch to generated output should carry an
   explicit note ("also needs to land in mcpify's `<template>.tera`")
   right in the commit, and a design doc for generated-repo work should
   state up front which parts of the repo survive a re-sync and which
   don't.

4. **A generator's own `CHANGELOG.md` entry is not the same as a
   `docs/DOC-GAPS.md` root-cause entry — track the gap, not just the
   fix.** This cross-check found roughly a dozen fixes below that are
   confirmed, dated, matching entries in mcpify's own `CHANGELOG.md` (the
   rustls crypto-provider panic, credential normalization, the setup-
   wizard TTY requirement, `allow-dirty`, the CI/release `timeout-minutes`
   gap, the README `--args` example drift, the multi-version Docker COPY
   gap, the ONNX Runtime release-target-matrix constraints, the initial
   CI/Docker hygiene pass, and the 8-bug auth/credential/embedding
   hardening commit) with **no corresponding entry in mcpify's own
   `docs/DOC-GAPS.md`**. The fix shipped and is traceable; the *why didn't
   the doc anticipate this* writeup never got done on the generator side,
   which means the next generated project (or the next person reading
   mcpify's planning docs to start a *different* project) has no way to
   learn the lesson without independently re-deriving it, the way this
   file just did. Closing that last mile — CHANGELOG entry triggers a
   DOC-GAPS root-cause writeup, every time, not only when a downstream
   repo's own gap-mining pass happens to notice it's missing — is as
   important as writing the CHANGELOG entry itself.

5. **Documented behavior is a claim about the code, not a statement of
   intent — verify it before writing it down.** `JIRA_DC_MCP_TOKEN` was
   documented as a working env-var override for three releases before
   v0.4.0's fix revealed it was never actually read — traced to the
   identical, dated bug in mcpify's own generator (v0.8.0), meaning every
   language target's generated README carried the same false claim at some
   point. The `call` usage example in the README was independently wrong
   twice (v0.2.9, then drifted again by v0.2.12 — the second occurrence is
   confirmed, via an exact-timestamp matching commit, to be the identical
   bug in mcpify's own README template). Prefer generating docs (or at
   least examples) directly from what the code does, or add a doc-example
   smoke test that actually invokes the documented command.

6. **Cross-platform (especially Windows CI) behavior needs its own
   explicit test-environment appendix, decided once, not rediscovered
   fix-by-fix.** From v0.5.3 through v0.7.9, nine separate commits across
   five releases fought the same underlying gap — Windows' file-locking,
   console/stdio, and TTY semantics differ from POSIX in ways nothing
   documented up front. This is *the same saga*, commit-for-commit
   traceable to matching fixes in mcpify's own Rust-target template
   (v0.8.2 through v0.11.11) — see mcpify's own `docs/DOC-GAPS.md` entry
   "Windows-specific file-locking/timing semantics unaddressed for the
   embedded store" and its Lessons item 5, which independently reaches the
   same conclusion this file's Lessons item 1 above reaches for transport
   contracts: write the cross-platform-behavior appendix once, in
   `architecture.md`, before any target's Windows CI goes red for it the
   first time.

7. **Before shipping a higher-level "guided workflow" feature on top of
   a generated low-level API surface, do one full inventory pass across
   the whole catalog and write it into the plan.** The original prompts
   feature (v0.6.0) shipped without a full re-review of the operation
   catalog, and the very next release (v0.7.0) had to add a whole missing
   cross-cutting workflow (project setup, spanning four existing prompts)
   plus nine per-domain gotchas the first pass missed. `docs/mcp-prompts-
   workflow-expansion-plan.md`'s "Catalog re-review method" section is a
   good template for this: group every operation by resource family,
   diff that against what's actually documented, *then* design. This
   lesson is specific to this repo's own MCP-prompts feature — mcpify has
   no equivalent "guided workflow" concept yet — so it has no counterpart
   in mcpify's own docs, unlike every other lesson in this list.

8. **A cross-repo bug found once should be tracked once, fleet-wide —
   this pair of documents (`CHANGELOG.md` + this file) is exactly that
   mechanism, and it needs to run in both directions.** Several fixes here
   (v0.4.4's OAuth2/Content-Length bug, v0.7.2's mutex poisoning) were each
   independently found in more than one generated repo before being traced
   to a shared template — evidence the mechanism is needed. But this
   cross-check also went the *other* direction for the first time: reading
   mcpify's own equivalent documents caught one entry below that should
   never have been tagged shared at all (the v0.1.1 `.gitignore` fix — see
   that entry) and confirmed roughly a dozen others that genuinely are
   shared but were previously undocumented as such anywhere (see Lessons
   item 4). Don't just tag a fix "probably shared" from its shape — check
   the generator's own history before asserting it, the same way this pass
   did.

## Dated entries

### 2026-07-26 (v0.7.10 – v0.7.11)

#### Doc gap
mcpify's own `docs/prd.md` REQ-2.3.7 ("Packaging & delivery") requires a
multi-stage Dockerfile and a CI/CD pipeline with automated publishing but
never states an architecture-coverage requirement (amd64 **and** arm64)
for the images that pipeline publishes, and never flags that QEMU-emulated
cross-architecture Docker builds are unreliable in CI — both surfaced only
after every generated project was already publishing single-arch images.

#### Resulting work
Two releases: v0.7.10 added QEMU emulation to build both architectures in
one job; v0.7.11 replaced that with Docker's documented
build-by-digest-then-merge pattern (native `ubuntu-24.04` +
`ubuntu-24.04-arm` matrix jobs, merged with `docker buildx imagetools
create`) after QEMU emulation itself proved unsatisfactory.

**(shared mcpify-template gap)** — already tracked, in more detail than
this entry, in mcpify's own `docs/DOC-GAPS.md`: see its "2026-07-26 -
multi-arch container images not specified (v0.11.12 - v0.11.14)" entry,
which lists the matching upstream template fixes (`v0.11.12` QEMU-based
first pass, `v0.11.13` golden-test sync, `v0.11.14` native-runner rewrite)
this repo's `v0.7.10`/`v0.7.11` mirror almost exactly, one day later.

### 2026-07-26 (v0.7.6)

#### Doc gap
Two distinct gaps landed in the same release. First: no doc noted that a
test binding to `http://127.0.0.1` with no explicit port (implicit port
80) is unsafe on Windows CI runners, where IIS's Default Web Site can
already occupy that port and make a "connection should fail" test wrongly
observe success — mcpify's `docs/architecture.md` §6 ("Testing Strategy")
never addresses port selection for network-touching generated tests at
all. Second: a Windows file-handle-release-timing retry in the store
lock-release test, which *is* part of the broader Windows-locking gap
covered below.

#### Resulting work
`test-connection`'s test now binds and drops a real `TcpListener` to
obtain a genuinely free port instead of assuming one; the lock-release
test's `remove_file` now retries.

**(shared mcpify-template gap)** — confirmed via a matching commit in
mcpify itself, same date: `98c6535 fix: format generation_fixtures.rs and
use an ephemeral port in cli_smoke's sentinel URL`, folded into mcpify's
own `v0.11.8` (`docs/CHANGELOG.md`: "Switched the `cli_smoke` test's
sentinel URL to an ephemeral port to avoid port collisions in CI... Added
a retry around `remove_file`..." — the same two fixes, same release). The
`remove_file`-retry half is listed under mcpify's own `docs/DOC-GAPS.md`
Windows-locking entry (its `v0.11.8` bullet), but **the port-collision-
with-IIS half is not mentioned there at all** — worth adding as its own
line, since "don't bind a test's sentinel URL to an implicit port 80" is a
distinct, reusable rule from the Windows file-handle-timing gap it happens
to share a release with.

### 2026-07-26 (v0.7.5)

#### Doc gap
mcpify's own `docs/v1-implementation-plan.md` made a deliberate, documented
decision to embed a full standalone copy of the component-schema library
into every operation's input/output schema, reasoned as "simpler and more
robust than cross-schema `$ref` resolution" — but never specified what
"self-contained" should mean once genuinely cyclic schemas are involved
(anything shaped like `LinkGroupBean`, which nests a group of issue-link
groups inside itself, has no finite fully-inlined representation), nor
that an earlier partial fix (localizing into `$defs`) wasn't actually
equivalent to full inlining.

#### Resulting work
Every `$ref` that isn't part of a genuine reference cycle is now
recursively inlined, matching a companion fix applied in the mcpify
generator itself.

**(shared mcpify-template gap)** — already tracked, in more detail, in
mcpify's own `docs/DOC-GAPS.md`: see its "2026-07-21 to 2026-07-26 -
self-contained schema/`$ref` handling took three iterations (v0.5.12,
v0.11.5, v0.11.7)" entry — this repo's `v0.7.5` fix is the direct
downstream landing of mcpify's `v0.11.7` (`fix(openapi): fully inline $ref
instead of localizing into $defs`), the third and final iteration in that
entry's own telling.

### 2026-07-21 – 2026-07-26 (v0.5.3, v0.5.5, v0.5.6, v0.5.8, v0.7.2, v0.7.6, v0.7.7, v0.7.8, v0.7.9)

#### Doc gap
mcpify's own `docs/architecture.md` §2 ("Data Layer") describes
`mcp_store.db` extraction/embedding without ever mentioning concurrency or
platform-specific file-handle semantics — nothing in `docs/prd.md` or
`docs/architecture.md` states that store extraction/rename must be safe
under concurrent calls, or that Windows releases file handles and treats
mutex poisoning differently than POSIX systems. This single undocumented
gap produced a nine-commit, five-release firefighting sequence in this
repo alone: a store-extraction race only Windows could hit (v0.5.3); a
stdio-transport test whose exact error text isn't portable (v0.5.5); the
*same* stdio test hanging for ~5 hours on GitHub Actions' Windows runners
specifically (v0.5.6); a cross-process store-rename race needing retries,
and the `setup` smoke test hanging the same way (both v0.5.8); mutex
poisoning on the shared store connection turning one flaky failure
permanent (v0.7.2); a Windows file-handle-release timing issue in a
lock-release test (v0.7.6); a `HOME`-env-var test race compounding the
same area plus a retry-budget widening from 1s to 10s (v0.7.7); a further
widening to 60s (v0.7.8); and finally accepting defeat and skipping the
test on GitHub Actions' Windows runners specifically (v0.7.9).

#### Resulting work
See `CHANGELOG.md`'s entries for v0.5.3 through v0.7.9 for each individual
patch. The cumulative shape: cache the resolved store path per process,
retry renames with escalating backoff, recover instead of propagate on
mutex poisoning, treat GitHub Actions' Windows runners as a distinct
environment from "Windows" in general, and accept that some contention
there isn't fixable from inside this crate at all.

**(shared mcpify-template gap)** — already tracked, commit-for-commit, in
mcpify's own `docs/DOC-GAPS.md` entry "2026-07-19 to 2026-07-26 -
Windows-specific file-locking/timing semantics unaddressed for the
embedded store (v0.10.5 - v0.11.11)", which lists the exact matching
upstream fixes this repo's sequence mirrors: `v0.8.2` (atomic extraction,
→ this repo's own earlier v0.4.3, listed separately below), `v0.10.5`
(this repo's v0.5.3), `v0.11.1` (this repo's v0.5.8), `v0.11.2` (this
repo's v0.7.2, mutex poisoning — also independently confirmed in
`bamboo-mcp-rs` per that commit's own message), and `v0.11.8`–`v0.11.11`
(this repo's v0.7.6–v0.7.9). mcpify's entry even names the same eventual
resolution ("stop asserting the behavior on that CI platform at all").

### 2026-07-21 (v0.7.3)

#### Doc gap
mcpify's own `docs/prd.md` REQ-2.3.7 describes a CI/CD pipeline but never
states that every workflow job needs an explicit `timeout-minutes` rather
than relying on GitHub Actions' 6-hour default ceiling as the only bound
on a hang — exactly what let the mutex-poisoning incident (see the entry
above) burn hours of CI time before being noticed.

#### Resulting work
Added explicit `timeout-minutes` to both `release.yml`'s build job (45

**(shared mcpify-template gap, and a genuinely new finding)** — confirmed

`v0.11.3`/`v0.11.4`), with `adf0b3c`'s commit message citing the identical
`bamboo-mcp-rs` incident this repo's own `v0.7.2` fix also cites. **This
does not have its own entry in mcpify's `docs/DOC-GAPS.md`** — it's only
reachable there as background color inside the Windows-locking entry
above, which doesn't mention `timeout-minutes` at all. Worth its own
dated entry there: "no CI-hygiene requirement anywhere in `prd.md`/
`architecture.md` says every generated workflow job needs a
`timeout-minutes`."

### 2026-07-20 (v0.6.0)

#### Doc gap
No doc covered this at all: the original 3-tool surface (`search`/`get`/
`call`) left all multi-step sequencing knowledge for Jira DC workflows —
e.g. "you cannot guess a transition id, it's workflow-scheme-specific per
project/issue-type/version, so `getTransitions` must be called for *this*
issue first," or "editing a workflow scheme creates a draft with no effect
until published" — entirely up to whichever LLM was driving the client, to
be re-derived from scratch every session. `docs/mcp-prompts-workflow-
plan.md` names this gap explicitly as its own motivation. mcpify's own
`docs/prd.md` §1.5 ("Core Capabilities — The 3 Universal Tools") defines
exactly this flat, sequencing-free 3-tool contract for *every* generated
target — meaning this specific gap (no way to express multi-step domain
sequencing on top of `search`/`get`/`call`) is latent in every
mcpify-generated project, not just this one, even though the *fix* here
(MCP prompts) is currently hand-built only in this repo.

#### Resulting work
Added the MCP **prompts** capability: a `jira_workflow` master prompt plus
10 domain sub-workflow prompts, each with agnostic (non-hardcoded-
operationId) phrasing to stay correct across the 6 supported API-version
catalogs.

**(repo-specific)** — tagged repo-specific because the guided-workflow
*content* is inherently Jira-domain-specific and mcpify's PRD doesn't
(yet) have any prompts-related requirement to check the mechanism against.
Flagged as a fleet-wide risk regardless: this repo's own plan doc notes
that because prompts were hand-added directly to generated output rather
than upstreamed into mcpify's generator, a future `mcpify sync` could
silently overwrite them unless the equivalent feature is later added to
the generator — the same risk that materialized for README content in the
v0.5.0 sync below. If mcpify's own team is looking for a good "next
capability" candidate, the fact that a fleet-wide latent gap (REQ-1.5's
sequencing silence) already got a real, working fix in one downstream
repo is exactly the kind of signal `docs/DOC-GAPS.md` Lessons item 8 above
argues should flow back upstream, not stay local to this repo.

### 2026-07-18 – 2026-07-19 (v0.5.0)
